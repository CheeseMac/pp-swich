# 01 · 产品理念与需求规格（PRD）

## 1. 愿景

让个人和企业把分散在网页、内部系统和数据库中的**经合法授权的 API 能力**逐步沉淀为一个可共享、可切换、可审计、可供 Agent 安全调用的能力网络。

核心标语：**Discover APIs · Switch Profiles · Protect Secrets · Empower Agents**。

`pp swich` 是**API 目录 + 连接管理器 + 安全能力路由器**，不是密码展示器、爬虫平台，也不是替代每个现有系统的身份授权机构。

## 2. 需要解决的痛点

1. 人可以通过网页使用系统，但很难列出实际在用的接口。
2. OpenAPI、Postman、HAR、数据库对象散落各处，无法持续归档去重。
3. 同一服务可能有多套环境、多组账号，用户切换繁琐。
4. Agent 想调用接口，却不能安全地拿用户密码、Cookie 或全权 API Key。
5. 已发现接口未必稳定、可靠、经允许，缺少审核发布和版本机制。
6. 企业担心跨租户、跨员工权限、密钥外泄、违规数据跨境传输。
7. 现有项目把真实密钥写在 `.env` 中，AI 编码助手可能直接读取并发送到模型上下文；团队需要在代码只写别名的前提下安全开发。
7. 新系统没有统一的 Agent 接入最低规范。

## 3. 目标用户 / 使用场景

| 人群 | 使用情境 | 关键收益 |
|---|---|---|
| 个人开发者 | GitHub / 测试服务 / 自建 API 的多账号切换 | 一键换连接档案，不复制粘贴 Key |
| 企业员工 | CRM、运营后台、文档平台等网页日常使用 | 从授权流量中发现可复用的接口 |
| 平台工程师 | 接入已有数据库和 HTTP 服务 | 统一契约、目录、鉴权、审计 |
| 安全管理员 | 控制各 Agent 能调用哪些系统 | 审核、最小授权、风险分级、事件追查 |
| Agent 开发者 | 希望用 MCP/HTTP 调用获批工具 | 可搜索、标准化、权限过滤后的工具目录 |
| SaaS 开发者 | 希望新系统自然兼容生态 | 提供 OpenAPI+身份协议即可接入 |

## 4. 必须完成的用户旅程

### UJ-01：导入一个未知网页的 API（首期）

用户选择某个自己有权访问的网站，在浏览器 DevTools 导出 HAR → 本地脱敏导入 → 系统自动按域名、路径、方法聚合并推断参数 → 用户审查 → 发布只读工具 → Agent 经独立连接授权后调用。

### UJ-02：一键切换账户 / 服务端点（首期）

用户在 `CRM` 页看到两个 Profile：
- `Work / Production / Alice`
- `Sandbox / Test / Alice`

点击 `Activate` → 服务端检查本人是否拥有目标 Profile / Endpoint 权限 → 更新活动绑定的版本 → 后续工具调用按新的连接档案执行。活动状态的作用域为 `workspace + principal + service + context_key`，不能影响其他用户。

### UJ-03：多人归集同一个 API（首期）

两位员工各自发现 `/api/customers/123`、`/api/customers/456`。系统将其作为同一 Operation 的证据，但保留发现来源和可见范围；接口契约可以共享，账号授权绝不合并。对外发布需满足系统所有者同意、契约验证、安全审批。

### UJ-04：数据库只读发现（首期后半）

管理员注册 PostgreSQL 只读连接 → Inspector 枚举允许访问的 schema / view → 创建候选只读工具 → DBA 审核列/行范围和资源配额 → 发布固定查询模板。Agent 不获取任意 SQL 执行权限。

### UJ-05：AI 编码助手参与开发，但不接触 `.env` 真实凭证（首期安全主线）

开发者将 `CRM_TOKEN` / `MODEL_API_KEY` 迁出仓库，使用 `ppswich` SDK 的 `invoke(capability, arguments)`；项目 `.env.example` 仅存工作区、能力和 Profile 别名。应用通过受信 Broker 的**独立身份**获取经授权的执行结果，服务端密钥从不返回给开发 Agent。若编码 Agent 与生产 Broker 同 OS 身份/网络权限，系统必须提示风险并要求隔离。

### UJ-06：新系统自描述接入（第二阶段）

开发者发布 OpenAPI 3.1 文档和可选 `x-pp-swich` 语义元数据 → 自动导入草稿 → 工具审核 → 发布到个人/团队/组织目录。

## 5. 优先级划分

| 级别 | 范围 | 说明 |
|---|---|---|
| P0 | HAR 导入、脱敏、候选 API、去重、审查、工具注册、Profile 一键切换、**Secretless SDK 与隔离执行器**、受控 HTTP 执行、权限、审计 | MVP 闭环 |
| P1 | Chrome 浏览器采集、数据库 Schema、MCP 适配、多租户团队共享、OpenBao | 可公开 Alpha |
| P2 | Local Connector、企业 SSO、审批流、策略表达式、异步调用、差异监测 | 企业 Beta |
| P3 | 插件生态、Agent 工具市场、自动化修复契约、国际化、SaaS 多区域 | 长期发展 |

**不在范围**：GUI/RPA、浏览器会话接管、破解签名接口、自动绕过访问控制、为第三方私有接口提供未经许可的商用代理。

## 7. 非功能约束（计划目标，不是实测结果）

- 安全：所有请求默认拒绝；端点白名单；最小授权；关键操作审计；不能记录明文凭证。
- 可靠性：异步工具调用必须幂等处理；超时明确；失败状态可查；不对有副作用请求无条件重试。
- 兼容性：稳定 JSON Schema / OpenAPI，MCP 作为适配出口；协议版本升级留兼容性测试。
- 可迁移性：单机 SQLite → PostgreSQL；Local SecretProvider → OpenBao，业务逻辑不变。
- 可用性目标：MVP 本地 P95 控制平面接口 < 500ms（不含外部 API）；生产目标上线前基准测试确定。
- 易用性：3 次点击内选择 Service 并激活已存在的 Profile；任何切换须显示环境、身份标签及危险提示。
- 隐私：不默认保存原始响应体；采集前授权；可按规则删除观察数据；留存策略可配置。

## 8. 成功指标

- 用户成功将至少 3 类不同来源（HAR/OpenAPI/Database）转为候选 Operation。
- 去重后的 Operation 可由多个发现者补充证据，而不会复制其密钥。
- 已授权 Profile 一键切换成功率、错误反馈和状态回显明确。
- 通过官方 MCP 客户端调用发布后的工具，原始凭证不出现在外部模型负载、工具描述、业务响应和日志中（通过合成蜜罐测试验证）。
- 所有 P0 安全测试通过，尤其跨租户 / 资源授权 / SSRF / 秘密注入 / 审批绕过。

## 9. 明确的权衡

- **先强契约、后 AI 自动推断**：自动生成仅作为草稿，审核和可执行性验证不可省略。
- **先标准接口、后网页私有 API**：正式授权 API 可靠性与合规性更可控。
- **先单机/Compose、后分布式**：不要为未知部署条件引入强制 Kubernetes。
- **先隔离身份、后共享目录**：共享“操作定义”，不共享“连接身份”。
