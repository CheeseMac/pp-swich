## 1. NET-13-F1：重复属性拒绝

评审的攻击示例完全复现：第二分支的 `profile` 覆盖第一分支，`private_note`
进入输出。修复采纳评审建议的最简可靠方案——**不做交集计算，只允许分支间
属性名完全不重叠的 allOf**：

- 合并前先做两两不相交检查，任一重复 → 整个 schema 判为不可解释；
- 根级重复 → 拒绝整个响应；嵌套重复 → 该字段置 None + dropped 标记；
- 完整 JSON-Schema 交集语义按评审建议明确排除在范围外（disjoint union
  是唯一受支持的 allOf 形状，注释与 docs 记录）。

测试用评审原始示例（根级）+ 嵌套重复 + 不相交正常合并三个方向锁定。

## 2. NET-13-F2：解析资源预算

评审指出的两个缺陷都属实：`depth` 只在 `$ref` 跳转时递增（纯深嵌套
递归爆栈），且重复内联无体积上限。四类独立预算全部落地：

| 预算 | 上限 | 超限行为 |
| --- | --- | --- |
| `$ref` 链深度 | 8（解析栈大小） | needs_review |
| 普通结构深度 | 64（每次递归 +1） | needs_review（不再 RecursionError） |
| 总节点数 | 20,000（单次解析累计） | needs_review |
| 数组长度 | 256 | needs_review |
| 解析后子树大小 | 512 KB（序列化字节数） | needs_review |

另按评审要求：**`$ref` 携带兄弟关键字一律拒绝**（内联会静默丢弃其验证
语义——包括 description 在内全部拒绝，规则最简且一致）。

## 3. PR-DEP-14：部署与出口强制控制

### 3.1 三层出口隔离（docs/28 完整版）

1. **应用层**（已有 + 本轮强化）：白名单/IP 钉扎/link-local 硬拒/
   `trust_env=False`/禁重定向；**新增 IPv6 包装归一化**——探测发现
   NAT64（`64:ff9b::/96`）内嵌地址确实绕过 `is_private`（Python 标准库
   不判 NAT64），`canonical_ip()` 现将 IPv4-mapped 与 NAT64 统一归一为
   内嵌 IPv4 再判定：`64:ff9b::a9fe:a9fe` → `169.254.169.254` → 硬拒。
   评审点名的验证面（DNS 切换/代理变量/重定向/IPv6/内网/元数据）逐项
   有回归测试看守；
2. **编排层**：`deploy/docker-compose.yml`——executor 只加入
   `internal: true` 网络（容器级无出口路由，应用层被绕过也无法出站），
   control 双宿；容器内代理环境变量显式清空；密钥全部经 `.env` 注入
   （缺任一必需密钥 compose 直接拒绝起服务）；
3. **主机层**：docs/28 提供 nftables 白名单样例；Windows/单机边界与
   跨内网多机（Edge Connector 前）的限制如实声明。

部署物验证状态：`docker compose config` 全量校验通过（服务/网络拓扑
正确、必填密钥守卫生效）；镜像构建因本机 Docker daemon 未运行未执行，
留待有 daemon 的环境首次部署时验证（如实记录，不虚报）。
