# 下一个会话的评审执行协议

## 推荐评审策略：功能优先、证据分级、少做重复架构审计

1. 以仓库当前 main 实际提交为准，读 `docs/31-HANDOVER.md` 的当前顶部基线、`docs/32`、`docs/33`、`docs/34` 与任何更新文档。
2. 比较新变更的代码和演示证据，不要因为原来发现过 `SEC-049～053` 就断言最新代码仍存在旧漏洞。
3. 核查 GitHub Actions Job 与提交号是否匹配，区分「开发者自报」「CI 成功」「评审人独立复跑」「真实客户端操作」。
4. 首先确认真实用户是否完成从 Discovery 到 Agent tools/call 的闭环；只有影响新功能的安全边界才作为本轮阻断项。
5. 对 FEAT-03 则必须确保秘密留在安全存储与受信执行器，不漏到 Agent 输出、UI、日志、模型请求、旧结果历史与配置。
6. 明确批复的等级：开发级/本地 Alpha/个人测试凭证/企业正式生产，不可含糊只说「通过」。
7. 把生产就绪条件单独交由 Gate R1 统一验收，不要因新功能 PR 又重新开全面网络架构工程。

## FEAT-05A 先做的快速实测

- 以 `admin` 身份创建演示 Agent，授权一个**后端实际存在的 GET 工具**。
- 用 UI 生成 MCP 配置；优先从 UI 复制，避免猜测客户端 config JSON 格式。
- 验证 mcp-adapter 当前真实参数：`ppswitch-mcp --control-url … --token …` 或相关环境变量。
- `tools/list` 应仅展示获授权且授权有效的 Published Tools。
- `tools/call` 用已知 GET 和合成参数实际调用，收到经 Guard 投影后的正常结果。
- 尝试未授权调用/撤销 Grant 后重试，必须失败。
- 亲自让 Claude Desktop 或 Cursor 启动 stdio 适配器；记录操作系统、客户端版本、运行日志与成功/失败状态（日志必须脱敏）。

## 批复范式（推荐）

- **当前交付**：提交号、功能页面、可运行用户操作；
- **已验证证据**：源码/CI/本地/真实客户端分级；
- **验收结果**：通过、附条件通过、失败，逐项写可复现原因；
- **生产限制**：是否仍禁止企业高敏感凭证；
- **下一 PR**：一条明确可交给编码 Agent 执行的实现目标，而非十项新架构愿望。
